# Kubernetes Control Plane

Ansible role responsible for bootstrapping the first Kubernetes control-plane node using `kubeadm`.

The role initializes the Kubernetes control plane, configures the administrative `kubectl` context, and validates that the Kubernetes API is reachable.

---

## Overview

The `kubernetes/control_plane` role is responsible for transforming a prepared Kubernetes node into the first control-plane node of the cluster.

The role builds on the infrastructure prepared by the previous Kubernetes roles:

```text
kubernetes/common
        │
        ├── Linux baseline
        ├── Kernel configuration
        ├── Sysctl
        ├── Swap disabled
        └── Time synchronization
        │
        ▼
kubernetes/containerd
        │
        └── containerd runtime
        │
        ▼
kubernetes/packages
        │
        ├── kubeadm
        ├── kubelet
        └── kubectl
        │
        ▼
kubernetes/control_plane
        │
        └── kubeadm init
```

---

## Responsibilities

This role is responsible for:

1. Detecting whether the control plane has already been initialized.
2. Initializing the Kubernetes control plane with `kubeadm`.
3. Explicitly configuring the container runtime used by kubeadm.
4. Creating the Kubernetes configuration directory for the administrator.
5. Configuring `kubectl` for the administrative user.
6. Providing a functional Kubernetes API endpoint.
7. Maintaining idempotent behavior across repeated Ansible executions.

This role does **not** manage:

- Kubernetes CNI
- Worker node joining
- Internal DNS configuration
- Ingress
- Applications
- Observability
- Cluster add-ons

Those responsibilities belong to subsequent stages of the Kubernetes platform implementation.

---

## Architecture

The control-plane bootstrap follows this architecture:

```text
                         k8s-cp-01
                             │
                             │ kubeadm init
                             ▼
                 ┌────────────────────────┐
                 │ Kubernetes Control     │
                 │ Plane                  │
                 │                        │
                 │ kube-apiserver         │
                 │ kube-controller-manager│
                 │ kube-scheduler         │
                 │ etcd                   │
                 └────────────┬───────────┘
                              │
                              │ kubelet
                              ▼
                         containerd
```

The Kubernetes API is exposed by the API server on:

```text
https://192.168.0.130:6443
```

## Prerequisites

The control-plane node must already have:

- Linux baseline configured
- Kubernetes kernel parameters configured
- Swap disabled
- Time synchronization configured
- containerd installed and running
- Kubernetes packages installed
- `kubeadm` available
- `kubelet` available
- `kubectl` available

These requirements are provided by the preceding Kubernetes roles.

The main variables are defined in:

```text
defaults/main.yml
```

Current configuration:

```yaml
---
# Kubernetes control plane role defaults

kubernetes_cluster_name: kubernetes

kubernetes_kubeconfig_directory: /etc/kubernetes

kubernetes_admin_kubeconfig: /etc/kubernetes/admin.conf

kubernetes_kubelet_service: kubelet

kubernetes_admin_user: debian

kubernetes_admin_home: /home/debian

kubernetes_admin_kubeconfig_user: /home/debian/.kube/config
```

### Cluster Name

```yaml
kubernetes_cluster_name: kubernetes
```

Defines the logical Kubernetes cluster name.

This variable is not passed to `kubeadm init` today, so it has no effect; `kubernetes` is also the kubeadm default cluster name. `kubernetes_kubeconfig_directory` and `kubernetes_kubelet_service` are likewise defined but not used by the tasks.

### Kubernetes Administrative Kubeconfig

```yaml
kubernetes_admin_kubeconfig: /etc/kubernetes/admin.conf
```

This file is generated by `kubeadm init` and contains administrative credentials used by `kubectl`.

### Administrative User

The current Kubernetes administrator is:

```yaml
kubernetes_admin_user: debian
```

The corresponding home directory is:

```yaml
kubernetes_admin_home: /home/debian
```

The user's kubeconfig is:

```yaml
kubernetes_admin_kubeconfig_user: /home/debian/.kube/config
```

## Control Plane Bootstrap

The role detects whether the control plane has already been initialized by checking:

```text
/etc/kubernetes/admin.conf
```

The bootstrap logic is:

```text
/etc/kubernetes/admin.conf
             │
       ┌─────┴─────┐
       │           │
     exists      absent
       │           │
       ▼           ▼
     skip       kubeadm init
```

This prevents `kubeadm init` from being executed repeatedly.

---

## kubeadm

The control plane is initialized using:

```bash
kubeadm init \
  --cri-socket unix:///run/containerd/containerd.sock
```

The CRI socket is explicitly configured because the cluster uses containerd as its container runtime.

The runtime relationship is:

```text
kubeadm
   │
   ▼
kubelet
   │
   ▼
containerd
   │
   ▼
/run/containerd/containerd.sock
```

---

## Kubernetes Configuration

After the control plane is initialized, `kubeadm` generates:

```text
/etc/kubernetes/admin.conf
```

The role creates:

```text
/home/debian/.kube
```

with permissions:

```text
0700
```

Then it copies:

```text
/etc/kubernetes/admin.conf
```

to:

```text
/home/debian/.kube/config
```

with permissions:

```text
0600
```

The resulting configuration is:

```text
/etc/kubernetes/admin.conf
             │
             ▼
/home/debian/.kube/config
             │
             ▼
           kubectl
             │
             ▼
      Kubernetes API
```

---

## Security Considerations

The Kubernetes administrator kubeconfig contains credentials capable of administering the cluster.

For this reason:

```text
/home/debian/.kube
```

is created with:

```text
0700
```

and:

```text
/home/debian/.kube/config
```

is created with:

```text
0600
```

The kubeconfig should not be committed to Git or exposed through logs.

## Ansible Integration

The role is executed by the Kubernetes playbook only for the control-plane group:

```yaml
- name: Configure Kubernetes control plane
  hosts: control_plane
  become: true

  roles:
    - role: kubernetes/control_plane
```

The complete Kubernetes preparation sequence is:

```yaml
- name: Prepare Kubernetes nodes
  hosts: kubernetes
  become: true

  roles:
    - role: base/linux
    - role: kubernetes/common
    - role: kubernetes/containerd
    - role: kubernetes/packages

- name: Configure Kubernetes control plane
  hosts: control_plane
  become: true

  roles:
    - role: kubernetes/control_plane
```

## Idempotency

Idempotency is a core requirement of this role.

The role checks:

```text
/etc/kubernetes/admin.conf
```

before running `kubeadm init`.

During the first execution:

```text
kubeadm init
    │
    ▼
changed
```

During subsequent executions:

```text
admin.conf exists
    │
    ▼
kubeadm init skipped
```

The second execution successfully skipped the initialization step:

```text
TASK [kubernetes/control_plane : Initialize Kubernetes control plane]
skipping: [k8s-cp-01]
```

The kubeconfig configuration can then be managed independently.

## Expected Cluster State

At the end of this stage, the cluster is intentionally in a partially configured state:

```text
                    Kubernetes Control Plane
                              │
             ┌────────────────┼────────────────┐
             │                │                │
             ▼                ▼                ▼
        API Server       Scheduler       Controller
             │
             ▼
            etcd
             │
             ▼
          kubelet
             │
             ▼
        containerd

Node: NotReady
CoreDNS: Pending
```

The `NotReady` state is expected until the Pod network is configured. In `playbooks/kubernetes.yml`, the `kubernetes/worker` role runs next, then `kubernetes/cni` deploys Cilium and all nodes become `Ready`.

## Scope

The implementation of this role is intentionally limited to the control-plane bootstrap.

It does not include:

```text
CNI
Workers
CoreDNS customization
Ingress
Storage
Observability
Applications
```

CNI, workers and CoreDNS customization are implemented by the `cni`, `worker` and `dns` roles.

Not configured by `kubeadm init` in this role: `controlPlaneEndpoint` (the API uses `https://192.168.0.130:6443`), Pod CIDR and Service CIDR (kubeadm default `10.96.0.0/12`). See the Implementation Notes in ADR-0002.
